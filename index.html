# Hermes Cron Operations

Operational playbook for diagnosing and maintaining Hermes cron jobs in a deployed environment. The skill is **about** the class of work that comes after you've written a cron job: how do you tell a syntax bug from a runtime bug from a data-source bug? How do you triage `last_delivery_error` fields that linger from a previous failure? How do you know if it's your script, your env, your delivery target, or your data feed?

## When to Use

- User says "dry-run my cron jobs", "why is my cron not working", "cron job failing", "delivery error"
- `hermes cron list` shows a job with `error: ...` or stale `last_delivery_error`
- A `no-agent` push script is silently dying (script exits 1 with no Telegram/Discord message)
- A backup / SSH / web endpoint that a cron job depends on has gone away
- A previously-working pipeline suddenly starts failing after a config change
- After adding a new platform (Discord, Slack, etc.) and wondering why cron still goes to old place
- Code audit / health check across the whole cron fleet (30+ jobs)
- **Bulk-switching LLM model/provider across cron jobs** (rotating API key, migrating from one provider to another, changing the global fallback chain, fixing `auxiliary.vision` config drift)

**Don't use for:** writing a new cron job (just use the `cronjob` tool / `hermes cron create`), or debugging a specific script's logic (use `systematic-debugging`).

## TL;DR — The 4-Layer Diagnostic Stack

Cron job failures have **four layers**, and the wrong fix targets the wrong layer. Always diagnose in this order:

| Layer | Question | Tool | Symptom |
|---|---|---|---|
| **1. Syntax** | Does the script even parse? | `bash -n script.sh` / `py_compile.compile(..., doraise=True)` | Import error on import, syntax error on run |
| **2. Runtime** | Does it run end-to-end? | `--dry-run` flag or `timeout 30 script.py` | Exit code 1, traceback mid-execution |
| **3. Data source** | Does the external API work? |
